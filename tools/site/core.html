RSOS Core v1

Eight state operations with neutral names, one compiled form, stable error codes and a state digest. A planning model writes the program from key names; the runtime executes it atomically and deterministically. Specified, implemented and tested; seven operations backed by pre-registered experiments.

Install: pip install rsoslang (0.4.0 and later include Core 1.0.0).

Quickstart

Parse either syntax into the IR, check its digest, execute it. The same program written in Core syntax or RSOS syntax has the same IR digest.

From an MCP client, the five state tools are rsos_state_new, rsos_state_prompt, rsos_state_apply, rsos_state_sync and rsos_state_get.

from rsoslang.core import (parse_core, compile_rsos,
    ir_digest, execute_ir, state_digest)

ir = parse_core(
    "reassign_where(field=owner, from=bruno, to=chen)")
rsos = compile_rsos("REHOST owner bruno chen")
assert ir_digest(ir) == ir_digest(rsos)

before = {"auth.owner": "bruno",
          "search.owner": "bruno",
          "cache.owner": "dara"}
after = execute_ir(before, ir)
# auth.owner and search.owner are now chen
state_digest(after)   # 2db9c91bc4cf on every replica

Operations

An operation is part of Core only when it is tested and backed by an experiment. copy is implemented and tested but no planner used it in A7 or A8, so it is supported and listed outside the Core layer until an experiment uses it.

{OPS}

Guarantees

Atomic steps

Every operation in a step succeeds and the new state replaces the old one, or the first error is returned and the state is unchanged.

Deterministic

Each operation is a pure function of state and program. No time, randomness, locale or key order in memory.

Values stay with the runtime

The planner sees key names only (an auditor model, where used, sees the values a step read and changed). The planner never reads, copies or computes a value, so it cannot mistype one.

Replica check without a model

Every copy carries a 12-digit state digest. A mismatched copy is repaired from the agreed state with zero model calls.

One program, one digest

Core syntax, RSOS syntax and the JSON IR are three forms of one program, identified by the SHA-256 of its canonical IR.

No guessing

The runtime never guesses a missing key or coerces a non-integer. It returns a stable error code the planner can act on.

Errors

Codes are stable within a major version. Each comes with a message written to be sent back to the planning model for one retry.

State digest test vectors

The first 12 hex digits of SHA-256 over the state as canonical JSON: keys sorted, values as strings, no insignificant whitespace, UTF-8. Any implementation must reproduce these.

The digest detects accidental drift between replicas. It is not authentication; use a full-length hash or a signature where tampering is a threat.

Lineage and status

Every operation carries one status. Only tested or executed operations backed by an experiment are part of Core; the registry records the evidence and the RSOS notation each operation came from.

  1. Proposed. Named and described.
  2. Specified. Precise meaning, inputs, outputs and errors.
  3. Implemented. Code exists.
  4. Tested. Conformance tests pass.
  5. Executed. Used by real agents in a pre-registered experiment, with published results.

Versioning and conformance

Core follows semantic versioning. Adding an operation is a minor change; changing semantics, an error code or an encoding is a major one. An implementation conforms when it passes the conformance tests, reproduces the digest vectors and keeps steps atomic.

Upgrading from 0.3.x

0.4.0 changes the state digest to the canonical encoding above, so digests from 0.3.x must not be compared with 0.4.0 digests. A SET on a missing source key and a SCALE to a fraction are now errors. rsoslang.state remains available as an alias of rsoslang.core.state.
